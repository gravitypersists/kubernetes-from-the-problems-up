A Deployment never touches a node directly. It writes down what it wants — three copies of this container, please — and walks away. Everything after that is other controllers noticing the gap between what was asked for and what exists, and closing it.

§ 02The scheduler’s two passes

When a new Pod appears with an empty nodeName, the scheduler picks it up. It doesn’t start the Pod; it only decides where the Pod should run, then writes that decision back to the API server. The kubelet on the chosen node does the rest.

Filtering

First, every node that cannot run the Pod is crossed off: not enough free memory, a taint the Pod doesn’t tolerate, a port already in use. What survives is the feasible set.

NOTEIf the feasible set is empty, the Pod stays Pending and the scheduler tries again later. Nothing is wrong with the Pod; the cluster is simply full.

Scoring

Then each feasible node gets a score from a handful of plugins, and the highest wins. Ties are broken at random, which is why identical Pods don’t all pile onto one machine.
