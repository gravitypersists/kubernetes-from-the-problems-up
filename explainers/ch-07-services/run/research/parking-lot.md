# Parking lot

- Service mesh, one sentence for naming it: Istio defines it as "an infrastructure layer that gives applications capabilities like zero-trust security, observability" and traffic management "without code changes"; meshes typically balance per request rather than per connection (model knowledge, unverified here). Ch 13. (https://istio.io/latest/about/service-mesh/)
- Headless Services: no cluster IP; the DNS name returns every selected Pod's address, used for databases and other stateful sets whose members must be reached individually. Ch 10. (https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)
- Long-lived connections stay on one Pod, so adding copies doesn't spread existing load until connections reopen. Ch 8 (autoscaling lag) and Ch 13 (mesh). (https://kubernetes.io/docs/reference/networking/virtual-ips/)
- DNS names include the namespace (`orders.<namespace>.svc.cluster.local`); a query without one only searches the caller's own namespace. Ch 11. (https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)
- Session affinity (`sessionAffinity: ClientIP`) keeps a client on one Pod; topology-aware routing and `internalTrafficPolicy: Local` keep traffic near or on the caller's node. Ch 13 / Ch 14 (cross-zone data charges). (https://kubernetes.io/docs/reference/networking/virtual-ips/)
- kube-proxy's default mode is `iptables`, moving to `nftables` in a future release; `ipvs` is deprecated (disabled by default from v1.40, removed in v1.43). Some providers replace kube-proxy with an eBPF network add-on. Ch 14 (upgrades) at most; network plugins are out of scope. (https://kubernetes.io/docs/reference/networking/virtual-ips/)
- Ingress NGINX's retirement as an ecosystem lesson: "about 50% of cloud native environments" relied on a controller maintained by "one or two people ... on their own time"; migration needed "planning and engineering time". Ch 13 ("every tool added is something to run and upgrade") and Ch 14. (https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/)
- Ingress2Gateway 1.0 (2026-03-20), the project's migration tool from Ingress to Gateway API. Ch 13. (https://kubernetes.io/blog/2026/03/20/ingress2gateway-1-0-release/)
- Gateway API's role split (infrastructure provider, cluster operator, application developer each own different kinds) maps onto platform team vs. product teams. Ch 11 / Ch 14. (https://kubernetes.io/docs/concepts/services-networking/gateway/)
- A cloud load balancer's own health checks and the "node liveness" behaviour of `type: LoadBalancer` are provider-defined, not set by Kubernetes. Ch 12 / Ch 14. (https://kubernetes.io/docs/concepts/services-networking/service/)
- Graceful shutdown: an old Pod is removed from the list "most likely before the Pod's containers exit", but callers with open connections or slightly stale rules can still hit it for a moment; apps should keep serving briefly after being told to stop. Ch 12. (https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/)
- A Service without a selector (pointing at an outside database by address) or `type: ExternalName` (an alias for an outside DNS name). Ch 10 (managed databases). (https://kubernetes.io/docs/concepts/services-networking/service/)
- Cross-provider load-balancer pricing and data-transfer charges. Ch 14. (https://aws.amazon.com/elasticloadbalancing/pricing/)
