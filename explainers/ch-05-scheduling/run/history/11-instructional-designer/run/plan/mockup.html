s-02 · § 02

What the scheduler counts

artefact → term → rule → predict → analogyo-1Part 1~4 min

Ch 4's sizes were requests the teams wrote down; memory and processor are counted separately; the scheduler rules out nodes, then picks the emptiest; it counts reservations, never use.

In Chapter 4's drawings every Pod had a size, and the scheduler looked for “a node with room”. Kubernetes didn't measure those sizes. Each team wrote them into its manifest when Fennel moved: how much memory and how much processor each copy should have set aside. Engineers call these numbers the Pod's requests. One unit of room in Chapter 4 was 2 GB of memory request.

NEW TERM · 01 / 04 (payoff)
requests
The memory and processor a Pod reserves on its node, written in its manifest. The scheduler places Pods by their requests, never by what they use.
memory and processor, counted separately · Chapter 4's “room”, written down

Fennel's nodes are 16 GB, 4-core machines; Pods can reserve about 13 GB and 3.9 cores of each, because part is kept back for the system. A Pod fits on a node only if both its requests fit in what that node has left unreserved (Fig. 02).

▸ D2 · Why can Pods reserve only about 13 GB of a 16 GB node? (collapsed) The operating system and Kubernetes' own programs need some; on one provider a 16 GB node keeps back about 2.7 GB.

The scheduler chooses in two steps: first it rules out every node without room for the Pod's requests; then it scores the rest and picks the best, at random between ties. With default settings, the best is the node with the most room left unreserved, and it prefers to spread a service's copies across nodes, as a preference only.

Moving day, explained (under Q1(b)): that's why storefront's three Pods went to three different nodes: 01 and 04 had the most room, so one Pod each; the third to 02, which had no storefront copy yet. Notice what the scheduler wasn't trying to do: fit Fennel onto as few nodes as possible.

One sentence: teams can add placement rules (keep copies apart, send Pods to particular machines, keep ordinary work off special ones); your engineers will tune these.

PREDICT · Check 02 / 09 · k-02
On a quiet Tuesday morning, Ari's dashboard shows node 02 at 15% busy. The Pods already on it have reserved all but 1 GB of its memory. A new Pod requests 2 GB. Will the scheduler put it on node 02?
  1. Yes: at 15% busy node 02 has lots of memory going unused, and the scheduler fills the quietest nodes first.
  2. No: the scheduler counts what the Pods on node 02 have reserved, and that leaves less than 2 GB.
  3. Only if every other node is busier: the scheduler compares how busy the nodes are right now and picks the quietest.
A and C: the scheduler never reads how busy a node is. B: “Right… it keeps that room for when the Pods' use rises, at the lunchtime peak.”

Reveal paragraph: the documentation says the scheduler refuses a node whose reservations are full “although actual memory or CPU resource usage on nodes is very low”, to protect the room for “a daily peak”.

ANALOGY Think of each node as a department's budget, each request as the budget a project reserves, and the scheduler as finance, which approves a new project only where reservations leave room. Whether the projects have spent their money doesn't come into it.
WHERE THIS ANALOGY BREAKS A finance team would move unspent money to where it's needed. The scheduler never does: reserved room a Pod isn't using stays reserved, at 3 a.m. as at the rush, and no other Pod can be placed in it.

The loop lens: the scheduler is one implementation of Chapter 4's pattern. It wants every Pod on a node with room for its requests; it sees Pods with no node and each node's unreserved memory and processor; it does rule out the too-full nodes, pick the emptiest, and write it in. And when no node passes the first step?

PREDICT · Check 05 / 09 · k-05
A month on, nodes 05 and 06 are still nearly empty. With default settings, what does Kubernetes do about them?
  1. Moves their Pods onto the fuller nodes and hands 05 and 06 back, since fewer nodes cost less.
  2. Nothing: the scheduler places only new Pods, and Fennel pays for both nodes until someone removes them.

A: nothing in Fennel's cluster packs Pods or gives nodes back. · B: “Right… Chapter 8 introduces a loop that can do it.” · C: the scheduler never moves running Pods.

Bin packing is fitting reservations onto as few nodes as possible; W-02 does it to count. The default scheduler doesn't: it spreads Pods out, which is safer but not cheapest. Packing is a setting engineers can switch on, and some fully managed modes pack for you.

Two kinds of idle: room no Pod reserved, and room reserved but unused. Morgan's “less than a third busy” is both together.

If you're billed per Pod: in most setups you pay for the machines; a few per-Pod options bill for what each Pod requests, not what it uses, so padding costs money there too. Some fully managed modes still bill per machine.

Morgan's answer: two extra nodes, rented because padded requests filled three on paper; a node's worth of spare room, which is a choice; and on every node, room kept back for the system. (A small fee per cluster also appears; Chapter 14.) Requests closer to what services use would mean fewer nodes, but not as few as possible.

▸ D5 · How common is this? (collapsed) One vendor's dataset (Datadog 2024, its own AWS customers, all containers on EC2): 83% of container spend on idle room, 54 points unreserved, 29 points over-requested. One community survey (CNCF 2023, about 100 self-selected respondents): 49% saw spend rise; over-provisioning the top cause at 70%. Single surveys, not industry averages.

▸ D6 · What does a per-Pod mode charge for, exactly? (collapsed) What each running Pod requests, per second on one provider; waiting Pods unbilled there, crash-looping ones billed; one provider rounds 1 core and 8 GB (plus 256 MB) up to 2 cores and 9 GB.

Room on purpose

explanation → questiono-2Part 1~1 min

Some idle room is insurance, and how much is a decision. Keeps Ch 4's promise about the room after 03:04.

A cluster with no spare room handles an ordinary Friday by leaving Pods waiting. Since 03:04 Fennel had run on three nodes with almost nothing spare. If a node had died during the rush, its Pods would have been replaced as at 03:04, and the replacements would have waited, like the dispatch Pod.

s-06 · § 06

Machines of different kinds: node pools

problem → name → figure → applyo-1Part 2~1.75 min

When a Pod outgrows a node, or some work can run on cheaper machines that can be taken back.

If orders keeps growing, its request may one day be bigger than any node has room for, and the documentation is blunt: such a Pod will never be placed. The answer is a bigger machine type. A node pool is a group of identical nodes within a cluster, and a cluster can have several, such as large-memory machines for the Pods that need them. Placement rules send Pods to the right pool.

Spot machines are cheaper, but the provider can take one back at short notice; teams give them their own pool and send there only work that tolerates interruption.

s-07 · § 07

Tuesday: when a Pod uses too much

artefact → chart → terms → predict → analogyo-2 o-3Part 2~3 min

Limits are the second number: a cap, not a reservation. Memory over it is killed and restarted in place; processor over it is slowed.

On Tuesday, Ari's dashboard shows orders-q2rw with a restart count of 3 and last state Terminated · Reason: OOMKilled · Exit code: 137. Engineers will recognise 137; what matters is the word before it.

Fig. 04 is orders' manifest section with both numbers: what each copy reserves (requests, 6 GB) and the most it may use (limits, 7 GB). A request isn't a cap: a container may use more than it requested while its node has room to spare; only a limit stops it.

NEW TERM · 03 / 04
limits
The most memory and processor a Pod's container may use. They cap use; they reserve nothing.
The second number in Fig. 04.

Each time orders' memory reached 7 GB, the operating system on the node stopped the container: it was “OOM-killed”, from “out of memory”. The node agent then restarted it, in the same Pod on the same node, not a replacement as at 03:04. Each restart was a short gap for customers; if it keeps happening, the waits between restarts grow, as with Chapter 4's crash-looping notifications.

NEW TERM · 04 / 04
OOM-killed
Stopped by the node's operating system for going over its memory limit (“out of memory”), then restarted in place.
Engineers see OOMKilled, and exit code 137.

Processor is different: at its processor limit a container is slowed down (engineers say throttled), never killed, because processor time can be handed out in slices and memory a program holds can't be taken back. “It got slow” and “it restarted” point at different numbers.

PREDICT · Check 07 / 09 · k-07
At the next sale, storefront needs more processor than its limit allows, and orders needs more memory than its limit allows. What do customers notice?
  1. Neither: the scheduler moves each one to a node with more room to spare.
  2. Both are killed and restarted, so pages and orders both fail for a moment.
  3. storefront slows down; orders is killed and restarted, failing orders for a moment.
A: the scheduler never moves running Pods; a limit caps the container wherever it runs. · B: only memory works that way.
ANALOGY Back to budgets: if a request is the budget a project reserves, a limit is the spending cap on its card. A project may spend beyond its reservation, up to its cap, while the department has money to spare.
WHERE THIS ANALOGY BREAKS Real caps work one way; Kubernetes has two. The processor card never declines, it slows the spending down; the memory card cuts the project off and starts it again from nothing. And spending above your reservation isn't safe just because it's allowed: when money runs short, the projects over their reservation are cut first (§08).

s-08 · § 08

Using more than you reserved

explanation → apply → lens tableo-2 o-3Part 2~2 min

Under-requesting's cost: when a node runs short of memory, its agent evicts the Pods furthest over their requests; their replacements may wait.

Besides starting and restarting containers, each node's agent watches how much memory its node has left. Ordinarily, Pods using more than they reserved is fine: there's room to spare.

If the node's free memory falls too low, its agent removes Pods to protect the node: an eviction. It goes first for the Pods using the most memory beyond what they reserved; Pods within their requests go last. Unlike §07's kill, an eviction removes the Pod; the ReplicaSet loop writes a new one, which the scheduler must place, and on a full cluster it waits, as on Friday. A request set below what a service uses doesn't save it room; it puts it first in line.

ANSWER: “Is that a leak or real growth? And what does it do to our node count?”

If it's a leak, a higher limit only delays the next kill, and a higher request rents room for a bug. If it's growth, a higher limit may be right; the documentation's advice is to check for a leak first, then raise the limit “and possibly” the request. Raising only the limit doesn't change where Pods go; raising the request reserves more room per copy, and on full nodes that can mean another node (try orders at 8 and then 12 GB in W-02).
