s-02 · § 02

What the scheduler counts

artefact → term → rule → predict → analogyo-1~4 min

Ch 4's sizes were requests the teams wrote down; memory and processor are counted separately; the scheduler rules out nodes, then picks the emptiest; it counts reservations, never use.

In Chapter 4's drawings every Pod had a size, and the scheduler looked for “a node with room”. Kubernetes didn't measure those sizes. Each team wrote them into its manifest when Fennel moved, declaring how much memory and how much processor each copy should have set aside. Engineers call these numbers the Pod's requests. storefront's two units of room appear here as its real memory request: 4 GB.

NEW TERM · 01 / 04 (payoff)
requests
The memory and processor a Pod reserves on its node, written in its manifest. The scheduler places Pods by their requests, never by what they use.
memory and processor, counted separately · Chapter 4's “room”, written down

Fennel's nodes are 16 GB, 4-core machines; Pods can reserve about 13 GB and 3.9 cores of each, because part is kept back for the system. A Pod fits on a node only if both its requests fit in what that node has left unreserved (Fig. 02).

▸ D2 · Why can Pods reserve only about 13 GB of a 16 GB node? (collapsed) The operating system and Kubernetes' own programs need some; on one provider a 16 GB node keeps back about 2.7 GB.

The scheduler chooses in two steps: first it rules out every node without room for the Pod's requests; then it scores the rest and picks the best, at random between ties. With default settings, the best is the node with the most room left unreserved, and it prefers to spread a service's copies across nodes, as a preference only.

That's why, when Ari applied storefront's manifest to the new cluster in Chapter 4, its three Pods went to three different nodes: 01 and 04 had the most room, so one Pod each; the third to 02, which had no storefront copy yet. Notice what the scheduler wasn't trying to do: fit Fennel onto as few nodes as possible.

One sentence: teams can add placement rules (keep copies apart, send Pods to particular machines, keep ordinary work off special ones); your engineers will tune these.

  2. No: the scheduler counts what the Pods on node 02 have reserved, and that leaves less than 2 GB.

A and C: the scheduler never reads how busy a node is. B: “Right… it keeps that room for when the Pods' use rises, at the lunchtime peak.”

Reveal paragraph: the documentation says the scheduler refuses a node whose reservations are full “although actual memory or CPU resource usage on nodes is very low”, to protect the room for “a daily peak”. New (#41): a request is a reservation, not a cap: a Pod can use less than it reserved, or more, as long as its node has room to spare. What stops it comes later.

ANALOGY Think of each node as a department's budget, each request as the budget a project reserves, and the scheduler as finance, which approves a new project only where reservations leave room. Whether the projects have spent their money doesn't come into it.
WHERE THIS ANALOGY BREAKS A finance team would move unspent money to where it's needed. The scheduler never does: reserved room a Pod isn't using stays reserved, at 3 a.m. as at the rush, and no other Pod can be placed in it.

The loop lens: the scheduler is one implementation of Chapter 4's pattern. It wants every Pod on a node with room for its requests (the desired state); it sees Pods with no node and each node's unreserved memory and processor (the real state); when the two differ, it rules out the too-full nodes, picks the emptiest, and writes it in. And when no node passes the first step?

Nodes go down, as node 03 did in Chapter 4. When one does, its Pods are replaced, and the scheduler has to place the replacements on the nodes that are left; if those are full, the replacements wait for room, like the dispatch Pod at the dinner rush. s-07 · § 06

Tuesday: when a Pod uses too much

artefact → chart → terms → predict → analogyo-2 o-3~3 min

Building on §02 (a Pod can use more than it reserves), limits are the cap: not a reservation. Memory over it is killed and restarted in place; processor over it is slowed.

On Tuesday, Ari's dashboard shows orders-q2rw with a restart count of 3 and last state Terminated · Reason: OOMKilled · Exit code: 137. Engineers will recognise 137; what matters is the word before it.

A Pod can use more than it reserves, but not without end. A manifest can also set limits: the most memory and processor each copy may use on its node. Here is orders' manifest with both: it reserves 6 GB and may use up to 7 GB.

NEW TERM · 03 / 04
limits
The most memory and processor a Pod's container may use. They cap use; they reserve nothing.
Over the memory limit: killed. Over the processor limit: slowed.

Each time orders' memory reached 7 GB, the operating system on the node stopped the container: it was “OOM-killed”, from “out of memory”. The node agent then restarted it, in the same Pod on the same node, not a replacement like the ones when node 03 died. Each restart was a short gap for customers; if it keeps happening, the waits between restarts grow, as with crash-looping, like we saw in Chapter 4.

NEW TERM · 04 / 04
OOM-killed
Stopped by the node's operating system for going over its memory limit (“out of memory”), then restarted in place.
Engineers see OOMKilled, and exit code 137.

Processor is different: at its processor limit a container is slowed down (engineers say throttled), never killed, because processor time can be handed out in slices and memory a program holds can't be taken back. “It got slow” and “it restarted” point at different numbers.

PREDICT · Check 06 / 08 · k-07

  3. storefront slows down; orders is killed and restarted, failing orders for a moment.

ANALOGY Back to budgets: if a request is the budget a project reserves, a limit is the spending cap on its card. A project may spend beyond its reservation, up to its cap, while the department has money to spare.
WHERE THIS ANALOGY BREAKS Real caps work one way; Kubernetes has two. The processor card never declines, it slows the spending down; the memory card cuts the project off and starts it again from nothing. And spending above your reservation isn't safe just because it's allowed: when money runs short, the projects over their reservation are cut first (§07).

Under-requesting's cost: when a node runs short of memory, its agent evicts the Pods furthest over their requests; their replacements may wait.

Besides starting and restarting containers, each node's agent watches how much memory its node has left. Ordinarily, Pods using more than they reserved is fine: there's room to spare.

If the node's free memory falls too low, its agent removes Pods to protect the node: an eviction. It goes first for the Pods using the most memory beyond what they reserved; Pods within their requests go last. Unlike the kill on Tuesday, an eviction removes the Pod; the ReplicaSet loop writes a new one, which the scheduler must place, and on a full cluster it waits, like the dispatch Pod at the dinner rush. A request set below what a service uses doesn't save it room; it puts it first in line.

Ari messages Jordan: “We need to bump memory limits on orders.” What would you ask? Think of one or two questions, then show the answer.

ANSWER: “Is that a leak or real growth? And what does it do to our node count?”

If it's a leak, a higher limit only delays the next kill, and a higher request rents room for a bug. If it's growth, a higher limit may be right; the documentation's advice is to check for a leak first, then raise the limit “and possibly” the request. Raising only the limit doesn't change where Pods go; raising the request reserves more room per copy, and on full nodes that can mean another node (in the sizing widget, from Fennel's requests, try orders at 5 GB and then 5.5 GB: 4 nodes, then 5). Then Fig. 07. Last line: “If your question was ‘how much more memory?’, that's the engineers' number. The two questions above decide whether more memory is the right fix, and what it costs.”

In short (five lines): two numbers per service, requests and limits · the scheduler places by requests, both counts on one node, never by use · no room means pending, and nothing makes room by itself · requests decide the node count; padding buys nodes, cutting below use buys evictions; some spare room is insurance · at the memory limit, killed and restarted; at the processor limit, slowed; before raising a limit, ask leak or growth, and the node count.
