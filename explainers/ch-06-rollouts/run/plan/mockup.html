Shipping without downtime: rollouts and rollbacks

For a somewhat technical manager (novice for infrastructure) · about 22 minutes planned (likely 23–25 built) · narrative article with one scrollytelling lane, a gated two-panel contrast figure and static figures · Chapter 6 of 15

Shape: One Thursday of catalog releases. A routine morning release (v62 → v63) is the chapter's one lane, on the pooled cluster canvas: the Deployment loop swaps three Pods one at a time, removing an old one only once a new one is ready, in one copy's worth of spare room. The afternoon release (v64) shows every price as $0.00: the reader first predicts what a crashing v64 and a $0 v64 would each do (k-04), then sees both outcomes side by side (Fig. 03). Rollback is shown as the record changing back (Fig. 05), not as a second lane, because it is the same process again. Rejected: two lanes (+2 min, the mechanism a third time); a hands-on settings widget (busywork); opening on the incident (spoils k-04).

Objectives:

  • o-1 Explain how a rolling update replaces one version with the next without downtime: the Deployment manages versions by managing ReplicaSets, brings new Pods up a few at a time, removes old ones only as new ones become ready, and needs spare room. checks: k-01, k-02, k-03
  • o-2 Predict which bad releases health checks stop (crashes, never ready: stalls) and which they don't (healthy but wrong: rolls out completely, m-09); tell a readiness probe from a liveness probe. checks: k-04, k-05, k-07
  • o-3 Explain rollback as declaring the old version again (rolled out the same way, from the kept ReplicaSet), what it assumes (old image kept; tags don't move) and what it doesn't undo (the 23 $0 orders). checks: k-06, k-07

s-02

One record per service: the Deployment

artefact → term → mechanism → lenso-1

Recall Ch 4's ReplicaSet, show the Deployment that wraps it, explain "one ReplicaSet per version", fill in the lens, and say where a new version comes from.

In Chapter 4, Ari's manifest for storefront was a ReplicaSet: keep this many identical copies of this Pod. Engineers rarely write one themselves. Fig. 01 shows catalog's.

TERM 01 · Deployment (payoff variant): "A record of which version of a service should run, and how many copies. Its loop gets there by keeping one ReplicaSet per version and resizing them." Back: "What engineers write instead of Chapter 4's ReplicaSet."

Change the Pod description (usually the image line) and the Deployment loop makes a new ReplicaSet for the new version, then makes it bigger and the old one smaller. Changing only the number of copies doesn't start this.

Lens: wants the version and copies its record names · sees its ReplicaSets and how many of their Pods are ready · does: moves copies to the new version's ReplicaSet, a few at a time.

Where versions come from (light): a merge → the build pipeline (engineers call it CI) builds catalog:v63, pushes it to the registry (images never change once built, Chapter 2), and writes the tag into the Deployment's image line. That edit is the whole release.

s-04

Room to ship

rule → applyo-1

State the default pace and its cost in spare room; let the reader predict what happens with no room.

By default a rolling update may run up to a quarter more Pods than wanted (rounded up) and let up to a quarter be unavailable (rounded down). For three copies: one extra, none short. At least three ready at every moment, at most four in all.

The extra Pod needs room: 2 GB and a quarter core. Room kept free as insurance (Chapter 5) is also room to ship.

Debrief (after k-03): the v63 Pod waits, pending; v62 keeps serving; the release doesn't happen until someone makes room. Question for the list: "Do we keep enough spare room to release during the busiest hour?"

D2 (collapsed) "What about a service with more copies?" — four copies: one extra and one short; moves roughly two at a time, at three of four for a while (hedged).

APPLY · k-03
Suppose the cluster were as full as on that Friday at 17:45 in Chapter 5, when a dispatch Pod waited for room: no node has 2 GB free. With the default settings, what happens when the pipeline writes catalog:v63 into the record?

B · The v63 Pod waits, pending; the three v62 Pods keep serving, and the release waits for room. (answer)

s-05

What "ready" means

contrasting cases → term → applyo-2

Open up the check behind READY: readiness (traffic, no restart) vs. liveness (restart), run by the node agent; what happens with no probe; apply it.

How did the loop know the first v63 Pod was ready? It read a result. The node agent on each node runs checks the team wrote into the Pod description, again and again (by default every ten seconds).

TERM 03 · readiness probe: "A check, written by the team and run by the node agent throughout a Pod's life, that decides whether the Pod may be sent traffic." Back: "Ready for traffic. Not 'correct'."

While it fails the Pod keeps running but is sent no requests (by a loop we'll name in Chapter 7), and a rollout doesn't count it. The liveness probe asks "still alive?"; when it fails, the node agent restarts the container: the job "noticing a container that's running but stuck". With no probe at all, a container is treated as passing: ready once running.

APPLY · k-05
During Friday's rush, one catalog Pod loses its connection to the database for a minute. catalog's readiness check asks whether the app can reach its database; its liveness check asks only whether the app is up and not stuck. What happens to that Pod?
A · The node agent restarts its container, as it restarted notifications in Chapter 4, until the database answers again.
B · Nothing restarts it; customers' requests go to the other two Pods until its check passes again. (answer)
C · The Deployment loop replaces it with a fresh Pod on another node, because one of its three copies has failed.

s-06

Two ways to be bad

predict → reveal (B4) → model → analogyo-2

Confront m-09: a crashing v64 stalls, a $0 v64 rolls out completely; availability, not correctness; stalled isn't rolled back; checks test what they were written to test.

The fair part: never fewer than three ready Pods; a new Pod took over only after its check passed. Tempting to conclude a finished rollout must be fine: "it passed its health checks".

(Locked until k-04.) Fig. 03. The second panel is what happened on Thursday at 14:02.

Why: a crashing container never becomes ready, so no v63 Pod is removed. The $0 version answered its check with a success code; a check passes on the status code alone, and nothing in Kubernetes looks at what the app sends back. catalog's check never looks at a price. A rolling update protects availability, not correctness.

Stalled isn't rolled back: the crashing Pod keeps crash-looping, v63 keeps serving, and someone has to roll back or ship a fix. D3 (collapsed) "How long does Kubernetes wait on a stuck rollout?" — 10 minutes by default, then only a "failed to progress" mark.

ANALOGY aside: a shift change: the manager sends the morning cashier home only once the afternoon cashier has signed in and opened a till. WHERE THIS ANALOGY BREAKS: a manager at the counter would notice a cashier charging nothing within a minute; the loop never sees a sale, only the check's result, and carries on while it passes.

Canary (a small share of customers first, while something watches) and blue-green (the new version beside the old, tested, then traffic switched at once): not built into a plain Deployment; tools such as Argo Rollouts add them.

The loop sees the gap it always looks for and closes it, using the v63 ReplicaSet it kept since 14:03; with the default settings, the same gradual way, which is why it took about a minute and needed the same spare room. Fig. 05.

TERM 04 · rollback: "Declaring an earlier version again. The Deployment rolls it out like any other change, from the ReplicaSet it kept." Back: "It changes what runs, not what already happened."

The loop doesn't know it's an "undo": no list of steps to replay; it compares the latest record with what runs now. By default it keeps its last ten old ReplicaSets.

D4 (collapsed) "Undo with a command, or change the file back?" — the command changes the record and leaves the files naming v64, so the next pipeline run ships v64 again; Riley changed the file back; GitOps (Chapter 13) makes that the only way.

s-08

What going back assumes

assumptions → questionso-3

The old image must still exist; the tag must still mean the same image; rollback doesn't undo the $0 orders. Each becomes a question.

The kept ReplicaSet holds the image's name; the image lives in the registry. Deleted, and the rollback stalls like any bad rollout. Fennel's registry deletes catalog images after 30 days.

An image never changes, but a tag can be moved; a digest names one exact image. Fennel's pipeline never reuses a tag.

Twenty-three orders went through at $0 and stayed that way; Jordan and Morgan honoured them. Chapter 10 is about data that outlives the Pods that wrote it.

Questions: "Do we keep old images for as long as we might need to go back, and do our tags ever move?" · "If a bad version runs for six minutes, what will it have written that rolling back won't fix?"

The conversation

think-then-reveal → recap → bridgeo-2o-3

Rehearse the conversation, recap, and look ahead to Chapter 7.

Friday morning's review. Riley, a little defensive: "The rollout passed health checks, so it wasn't the deploy."

Recap: Deployment = which version, how many; one ReplicaSet per version, shifted a few at a time, old Pods out only as new ones are ready, needing spare room · readiness = ready for traffic, liveness = still alive or restart · crashing or never ready → stalls; passes but wrong → rolls out completely · rollback = declaring the old version again, from the kept ReplicaSet, if the old image is there; it doesn't undo what the bad version did.

Bridge: "only ready Pods are sent traffic" was the work of a loop we haven't named. Every release gives catalog three new Pods with new addresses, and storefront has to find the ready ones at once. Chapter 7.
