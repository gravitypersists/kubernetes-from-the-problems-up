One app, one server

Standfirst (draft): Fennel's site went down for two hours on a Friday night, and nobody had touched the code. What lives on a server besides the code, and why that should worry anyone who depends on it.

For a somewhat technical manager (novice in infrastructure) · about 12 minutes of the reader's time · narrative article built around one hands-on widget · ToC: yes (7 sections) · READ 12 MIN · WIDGETS 01 · CHECKS 09

Shape: the chapter's lesson is a discovery: the code isn't the whole app, and the notes aren't the whole server. So the centre of the page is one widget in which you rebuild Sam's server from Sam's notes and watch identical code break. Prose carries the outage story, names things after you've met them, and holds the analogies and the business consequences. o-3 ("bigger server" or "VMs") is a pair of misconceptions, so it gets predict-then-reveal checks and one figure, not a second widget. Rejected: a free sandbox (you could miss the gaps; too long for 12 minutes) and a plain article (reading about gaps isn't finding them).

Objectives:

  • o-1 Explain why an app's behavior depends on the machine it runs on (runtime, libraries, config, disk), not just its code. checks: k-01, k-02, k-03, k-04
  • o-2 Predict what happens to the business when a single hand-built server fails, and ask: "If this box vanished tonight, how long until we're back, and who has to be awake?" checks: k-05, k-08, k-09
  • o-3 Explain why "just get a bigger server" or "add VMs" doesn't fix reproducibility. checks: k-06, k-07

§ 01 · s-01

Friday, dinner rush

story → pre-question → timelineo-2o-1

Feel the outage as a manager does (orders failing, one person scrambling), and guess why before any infrastructure idea appears.

"At 6:12 on a Friday evening, the busiest hour of Fennel's week, customers start seeing an error at checkout. Nobody has deployed anything since Tuesday."

  • Jordan forwards the first angry email to Sam, who is at dinner across town.
PREDICT · k-01 · think, then reveal
Nobody has changed a line of Fennel's code since Tuesday. So what could break checkout on Friday evening?
Answer shown: Something about the machine the code runs on. Fennel's code was fine. The server's disk had filled up, and the database could no longer record new orders.

After the timeline: "Deleting the logs took fifteen minutes. The other hour and forty-five went to reaching the one person who knew the server, and to that person finding the cause." Ends on the 23:00 fix: Sam sets up a nightly log clean-up by hand, "so this never happens again", and doesn't write it down.

What "the server" is

description → labelled diagramo-1

A picture of the machine before its contents: the app is a process on one machine, and deploying means getting new code onto it.

"Fennel's app runs on one rented computer in a data centre: the server. While it runs, the app is a process: the code loaded into the machine's memory, answering customers' requests, writing orders and log lines to the disk."

"To ship a change, Sam copies the new code onto that machine and restarts the process. That's a deploy."

"So far that sounds like code plus a computer. Look closer, and the code turns out to need a lot of help from the machine."

§ 04 · s-04

Why the notes fell behind

name after meeting → explain → analogyo-1o-2

Name what you just saw (dependency, drift, snowflake server) and explain "don't touch it", so the gaps read as how hand-built servers work, not as Sam's carelessness.

"Everything on that list besides the code is something the app depends on: its dependencies. That's the runtime it's written for, the libraries and tools it calls, and the config that tells it where things are. Same code, different machine, different behaviour."

"The notes weren't wrong when Sam wrote them. Then came the photo tool in May, the email key in August, and Friday night's fix: each a change made by hand and never written down. Engineers call this drift."

"And the holiday-sale setting? Even Sam can't say whether it matters. That's why you hear 'don't touch it' about servers like this one."

"A server made unique by years of hand-made changes is a snowflake server. Martin Fowler's phrase: 'good for a ski resort, bad for a data center.'"

ANALOGY · A1 · the original job description

Rebuilding from the notes is like replacing a long-tenured employee using only the job description they were hired with. The replacement does what's written. The duties that piled up over the years surface only when something goes undone.

Where this analogy breaks: a new hire notices gaps, asks around and uses judgment. A new machine does exactly what the notes say and fails silently. And the old server can't explain itself; even Sam doesn't know which settings still matter.

§ 05 · s-05

If this box vanished tonight

apply → explain → analogyo-2

From the server's side to the business's side: when the one hand-built machine is gone, the outage lasts until someone finds what the notes left out, and only one person can.

"Friday, the server was sick. Now imagine it's gone."

APPLY · k-05
Saturday, 2 a.m. The rented server's hardware fails for good. The code is safe in the repo, and Sam has the notes. When is Fennel fully back to normal?
A) As soon as someone copies the code onto a new server. · B) As soon as Sam has worked through the notes on a new server. · C) Only after Sam has also tracked down everything the notes leave out, often when customers hit the broken features.
A: "Your rebuilt machine had identical code, and photo uploads still failed." B: "You just did exactly that. The notes ran without an error, and three things were still missing, one of them the fix for Friday's outage." C: "Right. Two things set how long this takes: how much is missing from the notes, and whether the one person who can find it is awake."

After the reveal: the two factors, stated plainly. Rebuilding a snowflake is hard by nature (Fowler).

ANALOGY · A2 · bus factor

Managers know "bus factor": how many people could disappear before work stalls. Fennel's server has a bus factor of one: Sam.

Where this analogy breaks: here part of the knowledge isn't in anyone's head at all. It lives only on the machine, and even Sam doesn't know all of it.

WHY RECOVERY TIME · x-02

Martin Fowler once joked about a "certification" in which someone attacks your servers with a baseball bat, and the team is graded on how long until everything runs again. Recovery time, not uptime, is the measure.

§ 06 · s-06

"Couldn't we just…"

predict → reveal (×2) → figureo-3

The two fixes a manager reaches for each help with something real. Neither makes the server reproducible.

PREDICT · k-06
After Friday, Morgan offers to pay for a much bigger server, with ten times the disk. Which of Friday's problems does that solve?
A) All of them. The outage was caused by a full disk. · B) It pushes this particular failure months away, but Fennel still runs on one machine that only Sam can rebuild. · C) None. Disk space had nothing to do with it.
A: "More disk really does postpone this failure. But everything still runs on one machine, so any problem with it takes the whole site down. And that machine still can't be rebuilt from the notes. A bigger snowflake is still a snowflake." C: "Too harsh. Disk was the trigger."

"Bigger machines also have a ceiling, and their price climbs steeply near the top." (one sentence, c-11)

"Sam's idea: move to a cloud provider's virtual machine. That's a computer simulated in software, one of several sharing a big physical machine, each with its own operating system, and a new one is ready in minutes. The provider can also save a snapshot of its whole disk every night."

PREDICT · k-07
Sam suggests moving Fennel to a virtual machine at a cloud provider, with a snapshot of its disk taken every night. If that VM vanished tonight, what would getting back look like?
A) Click a button for a new VM, and you're done in minutes. · B) Restore last night's snapshot. You're back much faster, but the old clutter comes back too, anything changed by hand since the snapshot is lost, and still nobody is sure which settings matter. · C) No better than today. A VM is just a server with a different name.
A: "A new VM arrives blank. Someone still has to set it up, by hand unless something automates it (we'll name that later)." C: "Too harsh. A snapshot is an exact, bootable copy, so recovery really is faster."

ANALOGY · A3 · photocopying a cluttered desk

A snapshot is like photocopying Sam's desk: you get a copy fast, coffee stains and wrong notes included, and you still don't know which papers matter.

Where this analogy breaks: a snapshot is an exact, working copy, so it really does get you back faster than a photocopy would. The weakness is understanding the server, and the copy going stale as the real desk changes.

"VMs give you more machines, faster. They don't tell you what should be on them."

§ 07 · s-07

The conversation

apply ×2 → recap → open questiono-2

Rehearse the chapter's discussion move: answer "we should keep a runbook" with the question that measures the risk, and know which answer to listen for.

The Monday after the outage, Sam says: "We should keep a runbook for the server."

APPLY · k-08
The Monday after the outage, Sam says: "We should keep a runbook for the server." What's the most useful thing Jordan can say?
A) "Great. Once it's written, we're no longer dependent on you." · B) "Yes. And let's test it: if this box vanished tonight, how long until we're back, and who has to be awake?" · C) "Runbooks always go out of date. Let's not spend time on it."
A: "Written-down steps do help. Google's SRE team found they made repairs roughly three times faster than improvising. But every change made by hand afterwards puts the runbook behind the server, and the same team says no playbook is a substitute for engineers who can think on the fly." C: "They do drift, but they're much better than nothing. Test them, don't skip them."
APPLY · k-09 · think, then reveal
Sam answers your question. What answer should worry you, and what answer would reassure you?
Answer shown: Worrying: "Depends. If I'm reachable, a few hours, I think." A guess that depends on one person. Reassuring: "We rehearsed it last month. Jordan followed the notes on a spare machine while I watched without helping. Fifty minutes; we found two gaps and added them." A measured time from a real rebuild that didn't rely on Sam's memory.

Recap (three lines):

  • The app is the code plus everything it depends on, on one particular machine.
  • A hand-built server drifts away from its notes, and only rebuilding it shows how far.
  • Bigger servers and VMs help, but neither tells you what should be on the machine.

Open question (not answered): "If the app is the code plus everything on the machine, how do you ship all of it? A year later, Fennel has six engineers, and that question turns up every day." (Leads into Ch 2.)
