Same code, two machines

The reader predicts how one dependency version difference makes a “can’t reproduce” bug. Then the reader sees that one image on both machines makes them behave identically, so the bug surfaces on the laptop before release.

“Riley’s change works on the laptop. Here are the two machines, row by row. Predict, then see.” (Two sentences only; the widget carries the segment.)

PREDICT · Check 02 / 07 · inside the widget, state 1
Riley’s change passes every test on the laptop. The code is identical on both machines. What happens when the change ships to production?
  1. Photo upload fails in production, while on Riley’s laptop it keeps working, so nobody can reproduce it. (key)
  2. Photo upload works in production too: the code is identical, and it passed every test on the laptop. (m-19)
  3. The release refuses to install on production at all, because the two machines’ tools don’t match.
Feedback B: “That’s ‘the code is the app’ again. The tests ran on Riley’s laptop, with photo tool 7.0. Production has 6.2, which doesn’t know the option Riley’s code uses.”
PREDICT · Check 03 / 07 · inside the widget, state 2
Both machines now run the same image, fennel-app:v42, which contains photo tool 6.2. Riley tests the same change on the laptop. What happens?
  1. The tests pass on the laptop and photo upload fails in production, just as it did before the image.
  2. Photo upload works on both: the image packages the tool, so the version problem is solved. (tempting)
  3. The tests fail on Riley’s laptop, the same way the change would have failed in production. (key)
Feedback B: “The image doesn’t change what’s inside it. It holds 6.2, and Riley’s code needs 7.0. What it changes is where you find out.” Feedback C: “Right. Same image, same photo tool, same failure, but now on Riley’s laptop, before release, where it costs Riley ten minutes instead of costing customers a broken feature.”

s-03 · § 03

What goes in the image, and what doesn’t

name-after-meetingo-1o-2~2 min

Name what the reader just used (an image), say exactly what it contains and what it leaves out, and explain immutability as why it can’t drift.

“The sealed package in the widget is called an image: the app’s code packed together with what it needs to run, meaning the runtime, the libraries, tools like the photo resizer, and the files it starts with.”

  • Anyone who runs it gets exactly those versions. A new engineer runs the image instead of spending a week installing things.
  • Left out on purpose: settings that differ between places (database address, passwords) are handed in when the app starts, so one image serves staging and production. The data the app writes, like orders, is kept outside. “The code wasn’t the whole app, and the image isn’t either.” (m-19 revisit; config ≤ 2 sentences.)
  • Immutable: once built, it can’t be changed. A change means a new image with a new version label (v42 → v43), and the old one stays as it was. Nobody can hand-edit a built image, so it can’t drift like Sam’s server, and what was tested is exactly what ships.
ANALOGY · A1
Many companies don’t hand a new hire a setup checklist. IT gives them a laptop copied from one master setup, so everyone starts the same.
WHERE THIS ANALOGY BREAKS
An IT laptop starts drifting on day one, as people install things on it. An image can’t be changed at all; each copy starts fresh from it, and any change means a new image. And IT’s master copy includes the operating system’s core. An image leaves it out, which matters in a moment.

s-04 · § 04

Build once, run many: images and containers

figure → applyo-2~2.5 min

Tell the image (a package kept in a registry) apart from containers (the image running). One image runs as many containers, and changes made inside a container vanish when it’s replaced.

“Riley builds v43 once and puts it in a registry, a shared store of images. The laptop, staging and production each download (‘pull’) that same image.”

  • Running an image gives you a container: the app running as a process, walled off by the operating system with its own files from the image and its own view of what’s running. That’s the only sentence on internals.
  • One image can run as many containers. Production in Fig. 01 runs two.
  • A container can write files, but when it’s replaced, which every release does, those changes go with it.
  • (Optional, one line) “You’ll hear the name Docker in these conversations. The next chapter places it.”
ANALOGY · A2
The name comes from shipping containers. Before them, cargo was loaded piece by piece, differently at every port. After them, any ship, crane or truck moves the same sealed box without caring what’s inside. Engineers call the software version “build once, run anywhere.”
WHERE THIS ANALOGY BREAKS
A shipping container doesn’t care which ship carries it. A software container does: it needs a machine with the right kind of processor, and its settings are handed in when it arrives. Outside services, like the database, may differ too. “Run anywhere” means the inside is the same everywhere, not everything around it.
APPLY · Check 04 / 07
Saturday night, photo uploads break in production. Riley connects to the running container and fixes the problem by hand, inside it. It works. On Tuesday, Fennel releases its next version. What happens to Riley’s fix?
  1. It’s gone: Tuesday’s release starts new containers from the image, and the image never had the fix. (key)
  2. It stays: the fix was made on the production machine, so it remains there for the next release. (tempting: Ch 1 thinking)
  3. It spreads: changes made inside a running container are saved back into its image for next time.
Feedback A: “Right. A container starts fresh from its image, and changes made inside it disappear when it’s replaced. To keep a fix, put it in a new image. That’s also why containers don’t drift the way Sam’s server did.” Feedback B: “On Sam’s server it would have stayed, and that’s exactly how drift built up…”

s-05 · § 05

Not a small VM

predict → figureo-3m-01~2.5 min

Confront “a container is just a small VM”: containers share the machine’s operating system core, each VM carries its own. So containers are smaller, quicker to start and denser, with a thinner wall.

PREDICT · Check 05 / 07
Sam says a container is basically a small VM. Before you read on, which of these is closest to what a container actually is?
  1. A small virtual machine: it boots its own trimmed-down operating system, just a lighter one. (m-01)
  2. A compressed copy of a whole machine: it unpacks on any machine into an exact clone of the original.
  3. A walled-off process: it carries the app’s own files but uses the machine’s operating system core. (key)
Feedback A: “That’s the common picture, and it’s why containers get drawn like little VMs. But a container doesn’t boot an operating system of its own; it runs on the machine’s operating system core. That’s exactly why it’s small and quick to start.”

“That core is called the kernel: the part of the operating system that runs the hardware and every process on it.” (Gloss sits after k-05’s reveal, just before Fig. 02.)

  • Smaller and faster, typically: tens to hundreds of MB, starting in seconds, against a VM’s gigabytes and tens of seconds to minutes. Always hedged.
  • More per machine, because there’s no operating-system copy each. No number or multiple is given.
  • Thinner wall: one shared kernel, so a flaw in it is shared. Providers that run many customers’ containers side by side wrap each customer’s in a lightweight VM. For a company running its own code the trade-off is usually fine. Never “containers are insecure”.
  • In the cloud, the machine running your containers is usually itself a VM: layers, not rivals.
ANALOGY · A3
A VM is a house: its own foundation, plumbing and wiring. A container is an apartment: its own locked door, sharing the building’s foundation and plumbing. Cheaper and denser, and a burst main pipe reaches every flat.
WHERE THIS ANALOGY BREAKS
Containers usually run inside a VM, apartments inside a house, which the picture can’t show. And it says nothing about how fast a container starts.

s-06 · § 06

The conversation

apply → predicto-4local-01~2.5 min

Answer “Let’s containerize everything” with the machine-dies question, find out what does happen, and leave with the list of jobs containers don’t do, as the open question for Ch 3.

Quoted line, attributed to Sam: “Let’s containerize everything.”

APPLY · Check 06 / 07
At the planning meeting, Sam says: “Let’s containerize everything.” What’s the most useful thing Jordan can ask?
  1. “Great for consistency. So once a release passes staging, can we skip checking production?” (local-02)
  2. “Great for consistency. And what happens when the machine running those containers dies?” (key)
  3. “Great for isolation. If containers are walled off like VMs, can we stop paying for VMs?” (m-01)
Feedback A: “The image is identical in staging and production. But settings handed in at start, outside services like the database, and the machine’s processor can still differ. Passing staging is strong evidence, not proof.”
PREDICT · Check 07 / 07
So ask it. Saturday, 3 a.m.: the production machine running all of Fennel’s containers dies for good. What happens?
  1. The containers keep running: each is walled off from the machine, so its failure doesn’t reach them.
  2. The containers restart on another machine within seconds, since each can be re-created from its image. (local-01)
  3. Everything on it stops, until someone starts each of its containers again on another machine. (key)
Feedback B: “Half right. Re-creating a container from its image really does take seconds. But nothing in an image or a container notices the machine died, picks another one and starts them there. Someone has to.” Feedback C: “Right. Containers turn a day of rebuilding into minutes of restarting, a real improvement on Year 0. But someone still has to wake up, know what was running there, and start each one somewhere else. And anything written only on that machine is at risk.”
  • What’s left, as questions: Who notices the machine died? Who starts its containers again, and on which machine? What happens to anything written only on that machine? Once there are many machines, who decides what runs where? “Those jobs have a name. We’ll name it in the next chapter.”
  • In short (three lines): an image packs the app with what it needs, so a version gap shows up on your laptop, not in production · an image never changes; containers are copies of it, running, and start fresh each time · containers share the machine’s core: lighter than VMs, thinner walls, and they still die with their machine.
  • Closing line: “A year from now, Fennel runs its containers on eight machines, and that question becomes Sam’s 3 a.m. job.”
  • Sources list (Docker docs: image, container, persisting data, pull, multi-platform; Twelve-Factor dev/prod parity, dependencies, config; Google Cloud containers vs VMs; Agache et al., Firecracker, NSDI ’20) and a fiction note: Fennel, Riley, the versions and incidents are made up.
