What the jobs cost

table → explain → applyo-2~2 min

Tie each job to the symptom a manager sees, and show that the work grows with every service.

“Each job in Sam’s week shows up somewhere Jordan can see it.” → Fig. 01.

  • Idle machines, honestly: by hand, people keep room free “to be safe” and keep spares, because moving things later is slow and risky. Some of that room is insurance: on Saturday it was where orders went. How much is right is a Chapter 5 question. One industry estimate put the typical one-app-per-server machine at only 12–18% busy.

▸ D5 · Where does the 12–18% come from? A 2014 estimate by the NRDC, quoted by the US EPA’s ENERGY STAR programme, for US corporate data centres running one app per server. It’s not a measurement of container fleets, or of Fennel.

  • Work that grows with the service: Google’s site reliability engineers call manual, repetitive operations work that could be automated toil. It grows in step with the service, too much of it burns people out, and they aim to keep it under half of each engineer’s time.
  • The spreadsheet: Sam’s server notes from Ch 1 again. On Saturday it fell behind: it still says orders is on machine 03. “What if the record were the thing the machines act on, instead of a note about them? Hold that thought for the next chapter.”

s-06 · § 06

Where Docker fits

predict → figure → concrete explanationo-3 · m-02~1.5 min

Deliver Ch 2’s promise. Say concretely what each does: Docker’s tools build an image and start containers on the machine they’re run on; an orchestrator decides which machines in a cluster run each container, and keeps them running.

PREDICT · Check 08 / 09
You’ll hear “Docker” and “Kubernetes” in the same breath. Before reading on: how do the two relate?
  1. The same thing under two names: Kubernetes is what Docker grew into once it could run containers on many machines. (m-02)
  2. Different jobs, usually used together: Docker’s tools build images and start containers on one machine; Kubernetes runs them across many machines. (key)
  3. Rival products for the same job: a team runs its containers on one or the other, much like picking a cloud provider. (m-02)

A: “They’re separate projects. Docker appeared in 2013 as a set of tools for building and running containers. Kubernetes came from Google in 2014, to keep containers running across many machines.” B: “Right. Docker’s tools work on the machine you use them on: build the image, start a container there. Kubernetes decides which of many machines run each container, and keeps them running. Teams usually use both.” C: “Most teams use both: Docker’s tools to build images, Kubernetes to run them across their machines. Docker did make its own orchestrator, Swarm, and that is where the two competed.”

After Fig. 02:

  • “‘Docker’ is a set of tools for building images and running containers. On Riley’s laptop, docker build makes the storefront:v13 image, and docker run starts a container from it on that laptop. Docker’s tools act on the machine they’re run on.”
  • “Riley pushes the image to the registry. From there, an orchestrator such as Kubernetes decides which machines in the cluster run copies of it, starts them, and keeps doing the six jobs for them. Images follow an open standard, so Kubernetes runs an image no matter which tool built it. So the two aren’t competitors in the usual sense: most teams use Docker’s tools to build images and an orchestrator to run them across their machines.”
  • “Kubernetes was announced in 2014 at DockerCon, Docker’s own conference.”

▸ D7 · You may have read “Kubernetes drops Docker”. Since 2022, Kubernetes no longer uses Docker’s own software to start containers on its machines; it uses other software that does the same job. Images built with Docker run exactly as before.

▸ D8 · Didn’t Docker make an orchestrator too? Yes: Docker Swarm, which did compete with Kubernetes at the orchestrator’s job. That’s the one place they were rivals.
