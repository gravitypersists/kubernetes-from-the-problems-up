Last chapter ended on a question. A year later, Fennel runs its containers on eight machines. At 3 a.m. one of those machines dies for good. What happens to the containers that were running on it?

It’s Year 2. Fennel’s app used to be one piece of software. It’s now four services, separate parts that each do one job: storefront (the site and app customers use), orders, payments and dispatch (which assigns drivers). Each service runs as one or more copies, and each copy is a container started from that service’s image. Fennel pays for about eight rented machines to run them on. Sam keeps a spreadsheet that says which container runs on which machine.

Jordan doesn’t see containers or machines. Jordan sees four things:

  • Sam has been woken by a page at 3 a.m. more than once this month.
  • Release days start with a message from Sam in the team chat: “Nobody deploy anything, I’m updating storefront.”
  • The last time anyone needed the spreadsheet in a hurry, it was wrong.
  • Morgan, reading the bill, asks why Fennel pays for eight machines when half of them look mostly idle.

Here is one week of Sam’s job, step by step.

Here’s everything Sam did between Monday and Tuesday. How many different kinds of job are in this list, and what would you call each one? Settle on your answer, then show it.

  1. Found a machine with room for each of nine containers.
  2. Wrote each one’s machine into the spreadsheet and into the settings of the services that call it.
  3. Restarted the crashed dispatch copy where it was.
  4. Started orders and dispatch on other machines after machine 03 died.
  5. Passed orders’ new address to storefront.
  6. Swapped storefront’s three copies to v13, one at a time.
  7. Left three storefront copies running all week, sized for Friday’s dinner rush.

ANSWERSix kinds of job:

  • placing (1, and part of 4): finding a machine with room for each container.
  • restarting (3): starting a crashed container again where it was.
  • replacing (4): starting a dead machine’s containers on other machines.
  • connecting (2, 5): telling everything that calls a container where it is.
  • updating (6): swapping in a new version without downtime.
  • scaling (7): matching the number of copies to demand. Sam doesn’t, so Fennel pays all week for Friday’s three. Doing it by hand would mean adding copies every Friday and removing them afterwards.

The spreadsheet isn’t a job of its own. It’s the record of all six, and right now it still says orders is on machine 03.

If your list was shorter, the usual misses are restarting vs. replacing (one stays on its machine, one has to move) and connecting, which came along with every move.

Is that every job?

Real teams add more: noticing a container that’s running but stuck, handing each container its settings and passwords, and watching all of it. Chapters 6, 9 and 12 cover those.

§ 03 What the jobs cost

Each of the six jobs in Sam’s week shows up somewhere Jordan can see it.

Start with Morgan’s idle machines. When people place containers by hand, they leave room free on each machine “to be safe” and keep spare machines, because moving things later is slow and risky. Some of that room is insurance: on Saturday night, the free room on machine 04 is where orders went. How much spare room is right is a question for Chapter 5. Machines doing far less than they could is an old problem, though. One industry estimate, for data centres where each app had a server to itself, put the average server at only 12 to 18% busy.

Where does the 12–18% come from?

It’s a 2014 estimate by the Natural Resources Defense Council (NRDC), quoted by the US Environmental Protection Agency’s ENERGY STAR programme. It describes US corporate data centres running one app per server. It isn’t a measurement of machines running containers, or of Fennel.

Then there are the people doing the work. Google’s site reliability engineers have a name for manual, repetitive operations work that could be automated: toil. In their experience, toil grows in step with the service it supports, and too much of it burns people out, so they aim to keep it under half of each engineer’s time. Almost everything Sam did between Monday and Tuesday was toil.

And then there’s the spreadsheet. It’s Sam’s server notes from Chapter 1 again: a record kept by hand, of a system that changes every time something fails. A record like that falls behind, and on Saturday night this one did. It still says orders is on machine 03.

What if the record were the thing the machines act on, instead of a note about them? Hold that thought for the next chapter.

§ 04 Software that does the jobs

What would help Sam isn’t a faster Sam. It’s software that does the six jobs in Fig. 01 by itself.

Doing those jobs automatically, for as long as the containers run, is called orchestration, and software that does it is an orchestrator. An orchestrator doesn’t only act when someone releases a new version. At 3 a.m., when a machine dies, it starts the lost containers on other machines and passes on their new addresses.

New term · 01 / 03

orchestration · orchestrator

Doing the six jobs automatically, all the time, for as long as the containers run; and the software that does it.

You met it in §02: Sam’s week.

You give an orchestrator a group of machines, physical or virtual, and tell it how big each container is. It fits the containers onto the machines itself. That group of machines, treated as one pool of room, is a cluster. The four machines Sam used in §02 would make a small one.

New term · 02 / 03

cluster

A group of machines an orchestrator treats as one pool of room for containers.

You met it in §02: the four machines.

Both definitions say what an orchestrator does, not how it does it. How it manages all this with nobody at a keyboard is the next chapter’s subject.

ANALOGYThe word comes from music. A conductor keeps dozens of players starting, stopping and changing together, so the orchestra sounds like one instrument.

WHERE THIS ANALOGY BREAKSA conductor is one person giving every cue from the front, and every player still uses their own judgement. In an orchestrator, no single part gives every cue: separate parts each watch for one kind of work and act on it. How that work is split up is the next chapter. And no part of it uses judgement: it follows rules, so it will keep restarting an app that is broken.

§ 05 Its name is Kubernetes

The orchestrator this course is about is Kubernetes. It’s the name the course has been heading for since Chapter 1.

New term · 03 / 03

Kubernetes

An orchestrator: software that does the six jobs across a cluster, all the time.

placing · restarting · replacing · connecting · updating · scaling

Kubernetes came out of Google. Google had run its own services in containers for years, on an internal system called Borg. It later built a second system, Omega, to try out new ideas, many of which went back into Borg. One reason Google built Borg was to let different kinds of work share the same machines, so that more of each machine gets used and costs come down. That’s Morgan’s question about idle machines, asked at Google’s scale.

You’ll hear that Kubernetes is Google’s Borg, released to the world. It isn’t. Kubernetes was Google’s third such system, built new with lessons from the first two, and open source from the start. Borg and Omega stayed inside Google.

Google published Kubernetes as open source in 2014. In 2015, at version 1.0, Google announced it would give Kubernetes to a newly formed foundation, the Cloud Native Computing Foundation, which is part of the Linux Foundation, so no single company owns it. By 2024, tens of thousands of people from thousands of companies had contributed to it.

Does Google run on Kubernetes?

Google’s own services ran on Borg, at least as of 2016, when the designers of Borg and Kubernetes described both in a paper. Kubernetes was built for developers outside Google, including the customers of Google’s cloud business.

Kubernetes isn’t the only orchestrator. Docker Swarm and Apache Mesos are two others, and Chapter 14 compares the options.

How Kubernetes does the six jobs with nobody at a keyboard is the next chapter. First, a name you’ll hear alongside it.

§ 06 Where Docker fits

Last chapter said you’d hear the name Docker in conversations about containers, and that this chapter would place it. Commit to an answer before you read how.

PREDICTCheck 08 / 09

You’ll hear “Docker” and “Kubernetes” in the same breath. Before reading on: how do the two relate?

“Docker” is a set of tools for building images and running containers. On Riley’s laptop, docker build makes the storefront:v13 image, and docker run starts a container from that image, on that laptop. Docker’s tools act on the machine they’re run on.

Riley then pushes the image to the registry. From there, an orchestrator such as Kubernetes decides which machines in the cluster run copies of it, starts those copies, and keeps doing the six jobs for them. Images follow an open standard, so Kubernetes runs an image whichever tool built it. That’s why Docker and Kubernetes aren’t competitors in the usual sense: most teams use Docker’s tools to build images, and an orchestrator to run them across their machines.

Kubernetes was even announced at Docker’s own conference, DockerCon, in 2014.

You may have read “Kubernetes drops Docker”

Since 2022, Kubernetes no longer uses Docker’s own software to start containers on its machines; it uses other software that does the same job. Images built with Docker run exactly as before.

Didn’t Docker make an orchestrator too?

Yes: Docker Swarm, which did compete with Kubernetes at the orchestrator’s job. That’s the one place the two were rivals.

In short

  • Once many containers run on many machines, someone has to place them, restart and replace them, connect them, update them and scale them. By hand, that someone is Sam, at 3 a.m.
  • Each job lands on a manager’s desk: pages and burnout, idle machines, release days run from the team chat, and a spreadsheet that’s always behind.
  • An orchestrator does those jobs all the time, across a cluster of machines. Kubernetes is one, built from Google’s experience and now held by a foundation rather than one company. Docker’s tools build the images it runs.
