Year 2: eight machines and a spreadsheet

retrieval → storyo-1 o-2~1.75 min

RETRIEVE · Check 01 / 06
Last chapter ended on a question. A year later, Fennel runs its containers on eight machines. At 3 a.m. one of those machines dies for good. What happens to the containers that were running on it?
  1. They stop with the machine, and stay stopped until someone starts each one again on another machine. (key)
  2. They start again on one of the other seven machines within seconds, since each can be re-created from its image. (m-23)
  3. They carry on running, because each container is walled off from the machine underneath it.

A: “Right. A container is a process on one machine, so it stops with that machine. Nothing in an image or a container notices, picks another machine and starts it there. Someone has to.” B: “Half right. Starting a container from its image is quick once the new machine has downloaded that image. But nothing in an image or a container notices the machine died, picks another one and starts them there. Someone has to.” C: “The walls are between containers, not between a container and its machine. When the machine goes, so does everything running on it.” All end: “At Fennel, that someone is Sam.”

“Year 2. Fennel’s one app is now four services: storefront (the site and app customers use), orders, payments and dispatch (which assigns drivers). Each runs as one or more copies, each copy a container, on about eight rented machines. Which container runs where lives in a spreadsheet Sam keeps.”

What Jordan sees, as events: Sam paged at 3 a.m. twice this month; release days start with Sam’s team-chat message, “Nobody deploy anything, I’m updating storefront”; the spreadsheet was wrong the last time it mattered; Morgan, reading the bill, asks why Fennel pays for eight machines when half look mostly idle.

s-02 · § 02

Run the machines yourself

by hand, 3 phases + debriefo-1~4.75 min

The reader does Sam’s job by hand (placing, restarting, replacing, connecting, updating), feels where each one bites, then lists the jobs. The six jobs get their names only after the reader has done them.

Two lead-in sentences, then the widget. No prose after it: the debrief inside the widget ends the section.

Why these numbers: 4 machines × 6 room units; 9 containers = 14 units, so about half the room is free (the idle picture). The sizes guarantee no phase can dead-end and no container ever “fits nowhere” (that puzzle is Ch 5’s). In phase 3 there is never room for all three new copies at once, which nudges “start new, then stop old” without the page teaching it.

Chosen by rule, so the story always works: the 02:51 crash hits a dispatch copy on a machine that stays up; the 03:04 failure hits whichever machine the reader put orders on, so orders always goes DOWN.

EXPLAIN · think, then reveal · Check 02 / 06 · inside the widget, debrief
You just ran four of Fennel’s machines by hand. How many different kinds of job did you do, and what would you call each one? Settle on your list, then show it.

Model answer (revealed in place, with the reader’s own evidence from the log; the numbers here are one example run): 1 Placing, “You placed 9 containers on 4 machines.” 2 Restarting, “You restarted dispatch on machine 02. The machine was fine, so it stayed put.” 3 Replacing, “Machine 03 died at 03:04; you started its 3 containers somewhere else.” 4 Connecting, “You passed on 15 new addresses.” 5 Updating, “You swapped storefront’s three copies to v13, and the site never went down.” 6 Scaling, “You didn’t do this one. storefront runs three copies because Friday’s dinner rush needs them. Adding copies when traffic climbs and removing them after, every week, is the sixth job.” Then: “The spreadsheet is 5 rows behind.” Then: “Real teams add more: noticing a container that’s running but stuck, handing each container its settings and passwords, watching all of it. Later chapters cover those.” Under the list: “If your list was shorter, the usual misses are restarting vs. replacing (one stays on its machine, one has to move) and connecting, which rode along with every move.”

s-03 · § 03

What the jobs cost

table → explain → applyo-2~2 min

Tie each job to the symptom a manager sees, and show that the work grows with every service.

“Each job you did shows up somewhere Jordan can see it.” → Fig. 01.

  • Idle machines, honestly: by hand, people keep room free “to be safe” and keep spares, because moving things later is slow and risky, and some of that room is insurance (it saved you at 03:04). Industry estimates have long put a typical one-app-per-server machine at a small fraction of its capacity (a 2014 estimate: about 12–18%, US corporate data centres). No Fennel percentage. How much spare room is right: Ch 5.
  • Work that grows with the service: Google’s site reliability engineers call manual, repetitive operations work toil. It grows in step with the service, too much of it burns people out, and they aim to keep it under half of each engineer’s time (Google’s practice, not an industry survey).
  • The spreadsheet: Sam’s server notes from Ch 1 again. A hand-kept record of a system that moves every time something fails falls behind. Bridge question: “What if the record were the thing the machines act on, instead of a note about them? Hold that thought for the next chapter.”
APPLY · Check 03 / 06
Next month Fennel adds a fifth service, catalog, with two copies. Nothing else changes, and Sam still does every job by hand. What happens to the work you just did?
  1. Only the release work grows: catalog adds updates to coordinate, but it’s placed once, and 3 a.m. replacing is per machine, not per service.
  2. All of it grows: more containers to place and to restart or replace at 3 a.m., more addresses to pass on, more spreadsheet rows to keep right. (key)
  3. Very little grows: catalog runs in containers, so its image carries all it needs, and the machines don’t care how many services there are. (tempting)

A: “Placing isn’t once: every failure, move and update places things again. And a dead machine takes down every service on it, so more services means more to re-place each time.” B: “Right. Google’s site reliability engineers call this kind of work toil: manual, repetitive, and growing in step with the service. They aim to keep it under half of each engineer’s time, because too much of it burns people out. Each new service adds to Sam’s share.” C: “The image makes catalog easy to run on any machine. It doesn’t pick the machine, notice when that machine dies, or tell storefront where catalog went. Those are the jobs, and each new service adds to them.”

s-04 · § 04

Software that does the jobs

name after meeting → analogy → applyo-3~2 min

Name what the reader now wants (software that does the six jobs, all the time, across machines treated as one pool) as orchestration, an orchestrator and a cluster. Defined by what it does, not how.

“What Sam needs isn’t a faster Sam. It’s software that does the six jobs.”

“Doing those jobs automatically, for as long as the containers run, is called orchestration. Software that does it is an orchestrator. It doesn’t just act at release time. At 3 a.m., when a machine dies, it does the job too, with nobody at a keyboard.”

“You give an orchestrator a group of machines and tell it how big each container is; it fits them on itself. That group, treated as one pool, is a cluster: the four machines you just ran by hand were one.” How it does all this is the next chapter (one sentence).

Aside · ANALOGY: “Picture an operations manager for a chain of shops. They roster who works at which shop, cover for anyone who goes home sick, move a flooded shop’s staff to the others, keep head office told who is where, bring in a new procedure without closing a shop, and call in extra staff for the Saturday rush. An orchestrator is that job, done by software, around the clock, across a pool of machines.” WHERE THIS ANALOGY BREAKS: “A real manager uses judgement. They notice when something is off, and ask why the same person keeps going home sick. An orchestrator follows its rules, with no judgement: it will keep restarting an app that’s broken. And don’t picture one boss handing out every order. The next chapter shows how the work is really divided up.”

APPLY · Check 04 / 06
Riley says: “So an orchestrator is basically a smarter deploy script.” What does that picture leave out?
  1. That it builds the images too, so the deploy script and the image-building step can both be retired.
  2. That it only watches: it pages Sam sooner when a machine dies, while the moving is still done by hand.
  3. That it keeps working between releases: restarting, replacing and re-placing containers at 3 a.m., with nobody at a keyboard. (key; local-03 is the prompt)

A: “An orchestrator runs images; it doesn’t build them. Building stays with your build tools; more on that in a moment.” B: “Watching is part of it, but it does the jobs too: it starts the replacements itself.” C: “Right. A deploy script runs when someone releases, then stops. The jobs that cost Sam sleep happen between releases. An orchestrator keeps doing them all the time. How it does that is the next chapter.”

Its name is Kubernetes

payoff → historyo-3~1 min

Pay off the course’s promise: name Kubernetes after the reader has built its job list, and place it in history accurately.

“This is the name the course has been heading for. The orchestrator this course is about is Kubernetes. It does the six jobs you just did by hand, across a cluster, all the time.”

“Google ran its own services in containers for years, on internal systems called Borg and later Omega. It built Borg partly so different kinds of work could share machines, using more of each and cutting costs: Morgan’s question, at Google’s scale.”

“You’ll hear that Kubernetes is Google’s Borg, released to the world. Not quite: it was Google’s third such system, built new with lessons from the first two, and open source from the start. s-06 · § 06

Where Docker fits

predict → figure → explaino-3 · m-02~1.75 min

Deliver Ch 2’s promise. Confront m-02 (same thing, or rivals) by showing two layers that are usually used together.

PREDICT · Check 05 / 06
You’ll hear “Docker” and “Kubernetes” in the same breath. Before reading on: how do the two relate?
  1. The same thing under two names: Kubernetes is what Docker grew into once it could run containers on many machines. (m-02)
  2. Different layers, used together: Docker builds images and runs containers on a machine; Kubernetes runs them across many. (key)
  3. Rival products for the same job: a team runs its containers on one or the other, much like picking a cloud provider. (m-02)

A: “They’re separate projects. Docker appeared in 2013 as a tool for building and running containers. Kubernetes came from Google in 2014, to keep containers running across many machines.” B: “Right. Docker works where last chapter lived: build the image, run a container on a machine. Kubernetes works a layer up, keeping many containers running across many machines. Teams usually use both.” C: “Not in the usual sense: most teams use both, Docker to build and Kubernetes to run across machines. The one real rivalry was at the many-machines layer, where Docker’s own orchestrator, Swarm, competed with Kubernetes.”

After the reveal, Fig. 02, then:

  • “Docker” isn’t one thing but a set of tools: docker build makes the storefront:v13 image; docker run starts a container from it on one machine. Ch 2’s world.
  • The image goes to the registry; an orchestrator such as Kubernetes decides which of the cluster’s machines run copies, and keeps them running. Images follow an open standard, so Kubernetes runs them whichever tool built them. Most teams use both.
  • Kubernetes was announced in 2014 at DockerCon, Docker’s own conference. Not rivals in the usual sense; the one overlap is Docker Swarm, which did compete at the many-machines layer.
  • One sentence: since 2022 Kubernetes no longer uses Docker’s own engine inside the cluster, hence “Kubernetes drops Docker” headlines, but Docker-built images run exactly as before.

In short (recap box, three lines):

  • Once many containers run on many machines, someone has to place them, restart and replace them, connect them, update them and scale them. By hand, that someone is Sam, at 3 a.m.
  • Each job lands on a manager’s desk: pages and burnout, idle machines, release days run from the team chat, and a spreadsheet that’s always behind.
  • An orchestrator does those jobs all the time, across machines treated as one pool, a cluster. Kubernetes is one, built from Google’s experience and now a community project. Docker builds and runs the containers it keeps going.

Bridge: “Next: Fennel moves to Kubernetes, the same machine dies at 3 a.m., and nobody wakes up. The next chapter is how.”
