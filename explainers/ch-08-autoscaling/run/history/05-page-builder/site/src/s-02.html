§ 02 A loop that changes a number

Start with the first decision, the number of copies, and with something Kubernetes can measure. Each dispatch Pod reserves one processor core, as its team wrote in its requests in Chapter 5. On an ordinary evening a copy uses about 0.4 of a core, which is 40% of what it reserved; at a Friday rush, with too few copies, the same Pod might be asked for more than the whole core. Kubernetes can read that share for every Pod. It is a share of the Pod’s own reservation, not of the machine, so a service whose team never set a request gives this measurement nothing to stand on.

The dispatch team, with Ari, puts that measurement to work. Beside dispatch’s Deployment they add one more short record, which says three things: keep the average across dispatch’s Pods at about 60%, never run fewer than 3 copies, and never run more than 10. The record switches on a loop that works for dispatch alone, and engineers call a loop of this kind an autoscaler. The figure below shows the record on the left and, on the right, what the loop makes of three different readings.

The rule the loop follows is one of proportion. It compares the reading with the target and scales the number of copies by the same ratio, rounding up. Take the first reading in the figure: six copies, each at 90%. That is one and a half times the target, so the work would sit at the target if it were spread over one and a half times as many copies, and six become nine. The two limits fence the result in. The loop never goes below the minimum, however quiet the evening, and at the maximum it simply stops, however high the reading climbs.

It’s 17:50 on a Friday. dispatch has 3 copies, and its autoscaler (target 60%, minimum 3, maximum 10) reads an average of 120%. What does the autoscaler do?

The loop’s full name is the one on the first line of the team’s record: the HorizontalPodAutoscaler. Engineers say “the HPA”, and so will the rest of this chapter.

New term · 01 / 03

HorizontalPodAutoscaler · HPA

A loop that keeps one measurement of a service’s Pods near a target by raising or lowering the number of copies the service wants, between a minimum and a maximum.

Horizontal: more Pods, not bigger ones.

The HPA is one more implementation of the reconcile loop from Chapter 4, running in the control plane beside the others, and the loop lens fits it as it fits them. What it wants is its service’s Pods, on average, at the target. What it sees is how much processor each of those Pods is using. When the two differ, it rewrites one number in the record: the copies its Deployment wants. Everything that turns that number into running Pods is the work of loops you already know. The ReplicaSet loop writes the new Pod records, the scheduler gives each one a node, and the node agents start them.

Two practical things follow from how it measures. The first is its pace: by default the HPA looks about every fifteen seconds, and it leaves the number alone while the reading is within a tenth of the target, so small wobbles change nothing. The second is that requests matter again. Because the reading is a share of the request, a padded request of the kind Chapter 5 warned about makes a busy Pod look idle, and the loop acts late. The measurement doesn’t have to be processor use, though that is the common choice.

Does it have to be processor use? And other kinds of autoscaling

No. An HPA can read memory instead, or a measurement the team defines for itself, and when it is given several it works out a number for each and takes the largest. Where those measurements come from is a subject for Chapter 12.

You’ll also hear two other kinds of autoscaling named. Vertical autoscaling changes each Pod’s requests instead of the number of Pods; unlike the HPA, it isn’t built into Kubernetes and has to be installed separately. Event-driven scaling, for which KEDA is the usual tool, scales a service on events such as the length of a queue, and can take it all the way down to zero copies.
